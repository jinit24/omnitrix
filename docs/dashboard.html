Mission control

Inspect goals and evidence, talk to the manager, and review changes before they affect active work.

Start locally

omnitrix dashboard-user operator --users .omnitrix/auth/users.json
omnitrix --db .omnitrix/state.db dashboard --allow-control \
  --auth-users .omnitrix/auth/users.json --workspace-root .
# Separate owner process, initially waiting for commands:
omnitrix --db .omnitrix/state.db run GOAL_ID --steps 0 --hours 4

The default bind is loopback port 8765. Sign in with the account you created. Passwords are hashed; browser sessions use revocable HttpOnly cookies and CSRF protection. Resetting a password invalidates its sessions. Public HTTPS needs the single-host deployment.

What to inspect

ViewMeaning
OverviewCurrent objective, manager heartbeat, original and added criteria, exact-revision verification and final audit.
Manager chatSend messages, steer/pause/cancel tasks, run bounded decisions and review instruction changes.
TasksInspect hypothesis, scope, budget, findings, contradictions, blockers, source evidence and checks.
HierarchyActual manager assignments. Evaluators and test processes are identified separately.
KnowledgeRecorded findings and classifications. Revalidate sources before reusing them.
ActivityDecisions, progress and durable message receipts.

Control and approval

Create goals with mandatory criteria and an existing workspace inside the configured root. Code goals require a committed repository; creation grants no coding permission and starts no owner. One manager owns each database. The UI marks goals without an owner offline.

Policy replaces the complete instruction text; requirements add constraints and mandatory criteria. Review old/new text, affected tasks, evidence and approvals before accepting. A stale proposal requires new review. Code authorization stays explicit in the CLI; no deployment command is exposed.

Delivery and liveness

StateInterpretation
Queued / processingDurable request awaiting or being handled by the manager.
AcknowledgedReceipt handled; this does not mean the engineering goal succeeded.
Answered / failedRecorded response or error, linked to the request.
UncertainInspect state before resending. An unchanged retry reuses its request ID.
Online / stale / offlineOwner lock plus recent heartbeat, an old heartbeat, or no current owner.

State refreshes every five seconds. Disconnection retains the last snapshot and disables writes. A heartbeat proves responsiveness, not worker progress. Snapshots are read-only; their timestamps and experiment origin stay visible.

GitHub Pages

Pages shows three recorded real-model experiment runs. It cannot run the manager. Connect an explicitly allowed HTTPS backend using the optional bearer-token flow; same-origin password login is preferred on the actual backend site. Tokens are never stored in browser storage or published files.

Boundaries and checks

Recent-state reads are bounded to 200 goals and 200 records per category. Use CLI export for history. Reads use one read-only transaction; writes use the durable inbox. Source changes, goal/policy revisions and exact candidate SHAs constrain evidence. Executable checks and goal audit remain distinct.
