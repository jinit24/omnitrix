Continuous reliability

Outcome and evidence boundary

8 completed repair trials; 5 retained diagnostic failures. Trials use real GPT-5.4 research and manager calls, GPT-5.3-Codex workers, separate clean upstream test checkouts and real process restarts. The final confirmation set has 6 of 6 planned outcomes; all six completion gates passed: true. Median final-run time: 82.4 seconds; slowest: 123.3 seconds. Targets were median below 180 seconds and every run below 300 seconds. See every trial below; earlier failures are included in both results and spending.

The major failure was that continuation depended too heavily on the model reconstructing workflow state. It confused controller actions with unavailable tools, stopped despite existing authorization or retry credits, combined independent proof obligations, and replayed bloated context. The execution sandbox also hung on a minimal asyncio/thread bridge, making repeated full test runs there unproductive.

Native preflight and timeout trace retain the observed execution limitation; the exact underlying sandbox cause is unresolved.

What changed

  • Every decision uses bounded current state with durable recall and recent user guidance. Ordinary autonomy credits survive checkpoint restart.
  • The sole valid explicitly authorized implementation advances to coding and audit automatically. Independent current-revision checks still gate completion.
  • Recoverable research pauses receive concrete feedback. Repair investigations establish one current defect at a time; all mandatory requirements remain in executable verification.
  • Evidence fields accept identifiers rather than prose. Unknown citations and unsupported claims still fail independent review.
  • A bounded native execution preflight detects the observed async/thread limitation. Workers hand mandatory tests to the independent verifier instead of repeating a hung command.
  • Continuous campaigns save review times, rotate investigation targets after stalls, retain negative findings, back off on provider errors and record milestones without ending the goal. Spending is paced over the saved deadline; each request reserves its maximum cost.
  • After a confirmed interrupted or failed native turn, retained changes are checked against the original path authorization and all mandatory tests. A passing current-revision audit can finish the goal without another coding attempt; incorrect partial work remains blocked.
  • A process watcher restarts unexpectedly exited owners. Deadlines, evidence, attempts, costs and wake times survive; intentional stops remain terminal.

Reproduction

The repository contains benchmarks/oss_cases.json, benchmarks/reliability_protocol.json, scripts/validate_repositories.py and scripts/watch_campaign.py. Pin upstream clones to the recorded revisions. Use a separate test environment with pytest 8.4.2, Flask 3.1.2, Jinja2 3.1.6, Werkzeug 3.1.3, python-dotenv 1.2.1, Babel 2.17.0, trio 0.30.0, asgiref 3.12.1 and sqlparse 0.6.0.

.venv/bin/python scripts/validate_repositories.py --case jinja \
  --checkout work/jinja --test-python work/oss-venv/bin/python \
  --output work/NEW-TRIAL --allow-code-modifications
# Exit 75 marks the durable checkpoint. Start a NEW process with the same
# arguments plus --resume. For a delivery-loss trial, add --fault lost_completion.
.venv/bin/python scripts/watch_campaign.py \
  --db work/continuous-django/state.db --goal d6ff9fc07c5b43dfa393717396605eb3

Do not start a second watcher while the current one owns the database. Inspect with .venv/bin/python -m omnitrix --db work/continuous-django/state.db status d6ff9fc07c5b43dfa393717396605eb3. The campaign can be paused with the same DB and campaign d6ff9fc07c5b43dfa393717396605eb3 --pause.
