Durable research campaigns

Campaigns investigate a pinned local Git checkout using bounded discovery, hypothesis testing and fresh independent evaluation. They can remain active for days, with saved limits and an unexplored source catalog. The current Kafka investigation is an experiment; a multi-day reliability result has not been established.

Limits and money

The first invocation requires --days (up to 30), --decisions, --research-runs and --dollars (no greater than 25). Resume the same DB/goal without those flags. Saved deadline, consumed decisions, role attempts and dollar reservations do not reset.

Campaign manager/research/evaluation calls use a saved model and standard service tier. Existing contracts retain gpt-4.1-2025-04-14 ($2/M input, $0.50/M cached input, $8/M output). New continuous campaigns default to gpt-5.4 ($2.50/M input, $15/M output; cached input conservatively charged at full rate). Set --model only on creation. The saved model cannot change on resume. See the official GPT-4.1 and GPT-5.4 rates. Provider input-token counting includes the exact inline request and tool/schema definitions. Maximum output is 3,500 tokens; GPT-5.4 inputs above 272K tokens are rejected because long-context pricing is outside this contract. Maximum cost is reserved atomically before each paid request; actual usage releases the unused amount. Review these rates if provider pricing changes.

HTTP retries are disabled. A timeout, crash or lost response can have been billed: its full reservation stays held. The ledger may therefore stop below the cap. It excludes hosted tools, native Codex workers and other models, so those routes cannot create unaccounted campaign charges. Independent jobs using the same API account are outside this goal's ledger.

Large repositories and evidence

A streamed Git inventory builds a SQLite path catalog, with keyset pagination, component buckets and observed/unexamined counts. Full histories stay on disk; bounded manager state and recall tools prevent replaying the entire investigation. Excerpts and source counts describe observations, not exhaustive repository coverage.

omnitrix --db state.db campaign GOAL_ID --prepare-only \
  --evidence build/observations/context.txt \
  --evidence build/observations/service.log \
  --evidence build/observations/measurements.csv

Evidence paths must be existing UTF-8 files within the goal workspace, at most 32 MiB. Register exports explicitly; they retain a separate origin from tracked Git source. Record provenance, workload, units, measurement window, environment and limitations. Partition larger data. A local unit-test duration does not establish Kafka broker latency or production throughput.

Recovery and stopping

Use --continuous --review-seconds 300 on creation to save a recurring review schedule. Successful completion becomes a milestone requiring a newly tested hypothesis. Provider errors and stalled cycles trigger durable exponential backoff and different component suggestions. Review occurs after four decisions; unchanged evidence does not count as progress. Spending beyond a small initial burst is released proportionally across the saved wall-clock horizon, between decisions. This supports intermittent useful investigation over days; it does not promise continuous token generation or exhaustive issue discovery.

omnitrix --db state.db campaign GOAL_ID --days 3 --decisions 1000 \
  --research-runs 2000 --dollars 3 --continuous --prepare-only
python scripts/watch_campaign.py --db state.db --goal GOAL_ID

The watcher restarts an unexpectedly exited owner from the same DB. A terminal operator pause, deadline or exhausted budget stops it. SIGTERM/SIGINT on the watcher deliberately pauses the campaign. To recover watcher crashes or host reboots, run the watcher under a persistent host supervisor. A systemd service can use the following settings after replacing paths and the goal ID; keep credentials in a private environment file, outside the repository.

[Unit]
Description=Omnitrix continuous investigation
After=network-online.target
Wants=network-online.target

[Service]
WorkingDirectory=/absolute/path/omnitrix
EnvironmentFile=/absolute/private/path/omnitrix.env
ExecStart=/absolute/path/omnitrix/.venv/bin/python scripts/watch_campaign.py --db /absolute/state/campaign.db --goal GOAL_ID
Restart=on-failure
RestartSec=10
TimeoutStopSec=20

[Install]
WantedBy=multi-user.target

The DB and pinned checkout must survive reboot. This is a deployment example, not an installed service or demonstrated host-reboot result. See the live cross-repository results and sustained-run status.

omnitrix --db state.db campaign GOAL_ID
omnitrix --db state.db campaign GOAL_ID --pause
# After diagnosing a deliberate pause or false early completion:
omnitrix --db state.db campaign GOAL_ID --continue-paused

One owner holds the DB lock. Read-only SDK interruptions retain evidence and charged attempts; uncertain requests keep their cost reservations. Explicit continuation records the previous stop and resets only the stagnation window. Crashes and ordinary resumes preserve it. It does not authorize resetting limits or replaying native actions.

Deadline, decision, role-run and dollar exhaustion stop work. Ordinary campaigns pause after eight decisions without new evidence; continuous campaigns review and back off instead. New workers get their bounded chance to read before the stagnation check. The process needs a surviving host or an external process supervisor; no cloud scheduler or machine-to-machine recovery is included. Automatic code edits remain outside the continuous research spending contract; authorized implementations use isolated worktrees and mandatory independent verification.

Default completion minima require 20 observed files, 4 component buckets, 6 independently resolved hypotheses and 2 verified code mechanism findings. A mechanism needs a workload and falsification condition. Evidence gaps and measurements have separate categories. These gates prevent trivial data-gap completion but do not prove correctness or prevent every semantic reviewer error. Do not invent issues to satisfy them; budget/deadline exhaustion may produce an honest incomplete or negative result.

Longitudinal tracking

research-quality.html is generated from docs/research-quality.json. Each issue has its original diagnosis, current status, and dated observations, changes, tests and regressions. Experiment summaries keep their earlier timestamped versions. Model outcomes remain separate from deterministic guard tests and manual validation.

Campaign HTML checkpoints are replaced atomically every minute and on exit. The SQLite history and exported report include decisions, research queries/evidence, evaluations, inventory queries, challenges, recovery events and a per-request spending ledger. Preserve the DB and any .sessions.db sidecar with their WAL state before moving machines; keep the pinned checkout and exported evidence.
